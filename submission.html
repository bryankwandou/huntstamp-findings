The two with the most weight, both re-confirmed on the newer build:

- A market marked Resolved, with its order book closed and a final score of 2-6 on

  released is given a date with no relation to a settlement that already happened.

- /pm stops resolving to the market directory once any event has been opened. The cause
  is localStorage 'pm-events-store', which restores the stored event and rewrites the
  address bar. Removing that key restores the directory, so the root cause is isolated
  rather than just the symptom. This is the entry point named in the bounty brief, so
  anyone following a documentation link to /pm lands somewhere else.

Two findings were withdrawn rather than filed. Both withdrawals are documented in the
report rather than deleted:

- Mobile subcategory chips appeared non-functional. Re-testing showed the cause was my
  automation harness, not the application.

- I measured the /pm load event at 94s and then 136s through an instrumented browser and
  had written it up as a performance defect. An automated run on the same machine and
  connection then loaded the same route with loadEventEnd at 1,581ms and TTFB at 57ms.
  The slow figures were an artefact of my environment. The route does request 115 JS

Why the third bullet was removed

The earlier draft led with a performance claim: loadEventEnd at 94s and then 136s, against a same-session control load of 1.3s. That measurement was real, but it was not measuring the application. An automated Playwright run on the same machine and the same connection loaded the same route with loadEventEnd at 1,581 ms and TTFB at 57 ms, with the same 115 chunks.

The programme excludes issues caused by the reporter's own device or network. Sending that bullet to a CTO invites them to measure it themselves, find a second and a half, and discount the rest of the report by association. Removing it costs one finding and protects the other sixteen.
